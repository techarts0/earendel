# Earendel POSIX Compatibility Profile

This document describes behavior present in the repository, not the intended architecture. Earendel is a browser-hosted teaching simulation: its VFS, process table, syscalls, network, and devices do not provide host-kernel isolation or full POSIX conformance.

## Status vocabulary

- **Implemented (simulated):** behavior is wired through the in-browser kernel/service model.
- **Partial:** a useful subset exists, but observable behavior differs from POSIX or important cases are missing.
- **Not implemented:** no corresponding POSIX behavior is currently provided.

## Process and syscall surface

| Surface | Status | Current behavior and limits |
| --- | --- | --- |
| `read`, `write`, `open`, `close`, `stat`, `lseek` | Partial | Operate on Earendel VFS nodes and per-PCB descriptor maps. Capability and VFS permission checks apply to path access. Descriptors are numeric but are not host file descriptors. `lseek` supports `SEEK_SET`, `SEEK_CUR`, and `SEEK_END` for regular VFS files. |
| `fork` | Partial | Allocates a child PCB and one simulated user page, copies capabilities, and duplicates the descriptor table while sharing open-description offsets. It does not clone the parent's memory, environment, signal mask, or execution context. |
| `execve` | Partial | Reads a VFS path and returns its content/arguments to the caller. It does not replace the current process image. Shell dispatch separately interprets supported `.sh` and `.eaf` content. |
| `exit` and `waitpid` | Partial | Exit records an integer status and revokes the process endpoint/capabilities and simulated user page. A direct parent can block while the child runs; exit wakes one waiter and reaps the zombie. Orphans are adopted by simulated PID 1 and auto-reaped on exit. Invalid/non-child waits return `ECHILD`. This is a single-PID wait interface, not the full `waitpid(2)` option and status encoding contract. |
| `kill` and signals | Partial | `SIGKILL` and `SIGTERM` terminate the target with status `128 + signal`; `SIGSTOP`/`SIGCONT` change the simulated state; a small set of other signals is queued. There are no signal handlers, masks, delivery points, process groups, or full POSIX signal semantics. |
| Scheduling and memory | Partial | The scheduler tracks PCB states and a small simulated page table. It does not preempt JavaScript execution, clone address spaces, provide copy-on-write, or enforce a real MMU boundary. |
| errno and syscall ABI | Partial | Calls return `{ code, data, error }` from TypeScript; this is not a C ABI, register convention, `errno` location, or binary syscall interface. Some syscall error strings and trace labels remain simplified. |

The syscall numbers and current dispatch are defined in [`src/kernel/types.ts`](../src/kernel/types.ts) and [`src/kernel/syscall.ts`](../src/kernel/syscall.ts). Process behavior is implemented by [`src/kernel/taskScheduler.ts`](../src/kernel/taskScheduler.ts) and [`src/kernel/services/pmd.ts`](../src/kernel/services/pmd.ts); VFS descriptor behavior is in [`src/kernel/services/vfsd.ts`](../src/kernel/services/vfsd.ts). A runnable in-OS probe is installed at `/home/hello/tests/posix-process-conformance.bats`; run it with `bats /home/hello/tests/posix-process-conformance.bats` to exercise nested child output and exit-status/wait/reap behavior.

## Shell language

Earendel provides a POSIX-inspired shell implemented in TypeScript, not `/bin/sh` or Bash. The parser/interpreter supports a growing subset including command sequencing, pipelines, redirection, logical operators, variables, functions, conditionals, loops, and selected parameter expansions. Its BATS runner supports `@test`, `test_case`, basic assertions, and a `run` helper exposing `$status`, `$output`, and `$lines`; it is not full Bats-core compatibility. Pipelines pass strings between commands in sequence; they are not concurrent processes connected by kernel pipes. Job control, terminal process groups, complete quoting/expansion rules, and full shell grammar are not implemented.

Relevant implementation: [`src/core/shellParser.ts`](../src/core/shellParser.ts), [`src/core/shellEngine.ts`](../src/core/shellEngine.ts).

## WASM/WASI

The WASM runtime instantiates modules in the browser and supplies selected `wasi_snapshot_preview1` imports. Implemented imports include output, argument sizing, exit signaling, clock, and randomness. Several imports are stubs (for example `fd_close`, `fd_seek`, and environment retrieval); filesystem, process, socket, polling, and complete WASI error semantics are not available. Therefore “WASI-compatible” must be scoped to the imports actually implemented by [`src/core/wasmRuntime.ts`](../src/core/wasmRuntime.ts), not treated as general POSIX support.

## Capability and Agent boundary

Kernel authorization is deterministic and runs before the advisory Agent observation hook. Syscall observations are copied into a bounded queue (256 pending entries; oldest entries are dropped under pressure), and raw syscall string payloads are summarized before observers receive them. An Agent that exceeds a 35-second asynchronous response deadline is disabled so one stalled request cannot hold up observation draining; synchronous JavaScript still cannot be preempted on the main thread. Unknown processes do not get implicit syscall identity; VFS and network services also check capabilities at their service boundary. Interactive users get scoped VFS rights, read-only access to shipped Skills under `/skills`, and no network, device, or admin Capability by default. The LLM configuration (including its API key) is owned by root with mode `0600`; the driver and trusted status helper read it internally, and users configure it with `sudo vi /etc/llm.conf`. Authenticated root sessions receive the privileged profile, which is revoked when the shell returns to the prior user. Device writes go through vfsd and the originating process endpoint; direct VFS.writeFile() calls cannot trigger hardware effects. Hardware driver actions require path-scoped CAP_DEVICE_IO, network operations require CAP_NET_ADMIN, Wayland surfaces are owned by their creating PID and stale surfaces are pruned after process exit, and raw writes to /dev/skill are rejected in favor of the Skill command with explicit grants. cap-grant and cap-revoke require CAP_SYS_ADMIN; cap-list can inspect only the caller's own process unless the caller has that capability. Skill manifest permissions are requests: the caller must grant matching scopes/tools with skill --grant-read=PATH, skill --grant-write=PATH, skill --grant-tool=NAME, skill --grant-mcp=SERVER/TOOL, --grant-network, and/or --grant-memory. Effective permissions are restricted to the intersection of the manifest request and caller grants, then recorded in the session audit. UI launches without supplied grants receive no extra grants. Harness command/MCP actions and outputs are bounded, and manifest timeouts are capped at ten minutes.

In browser builds, EAF JavaScript now runs in a dedicated Worker. The Worker removes direct network, storage, device, and nested Worker APIs; OS-facing methods use RPC bound to the forked child PID and its scoped VFS. Calls crossing that RPC boundary are asynchronous. Execution has a 60-second deadline, and RPC count, aggregate message size, logs, and returned values are bounded. The app's Content Security Policy permits Blob Workers and same-origin module scripts while disallowing external module imports; deployments that replace this policy must preserve those restrictions. If Worker or Blob URL support is unavailable, browser execution fails closed. The Worker is a useful application sandbox, not a host-kernel security boundary: the browser controls CSP and resource quotas, same-origin module code remains within the trust boundary, and this simulation does not provide an MMU or protection against browser implementation flaws. Non-browser SSR/verifier execution still uses the in-process evaluator and must not be treated as an untrusted-code environment.

## Simulated subsystems

Networking and firewall decisions are educational simulations layered over browser APIs. HTTP(S) fetch uses browser `fetch` after simulated capability/firewall checks; browser policy still controls actual network access. DNS is simulated, WebSocket is browser-backed, WebRTC sockets are mocked, and `listen` returns a simulated listener identity. Raw sockets, arbitrary bind/listen/accept, packet access, and host firewall control are not provided.

## Verification policy

Build success proves TypeScript/Vite integration only. The repository includes a BATS process smoke suite at [`src/scripts/posix-process-conformance.bats`](../src/scripts/posix-process-conformance.bats), installed as `/home/hello/tests/posix-process-conformance.bats` and runnable with `bats /home/hello/tests/posix-process-conformance.bats`. The repeatable `npm run verify:posix` command runs that suite plus direct VFS/kernel and Skill checks. The latest run passed 36 checks, covering non-blocking syscall behavior with a stalled Agent observer, read-only access to shipped Skills, protection of root-only LLM credentials through VFS and syscalls, EAF fail-closed behavior without Worker support, Worker timeout cleanup, bootstrap syntax and browser API removal, CSP module-origin policy, cancellation of an in-flight network syscall, Wayland cross-process ownership, process-bound EAF syscalls, hidden mutable process state, bounded Skill input and output, caller-approved Skill scopes, caller cancellation of Skill and interactive Shell inference, stopping later shell statements after cancellation, explicit MCP and remote-LLM failure handling, cancellable `find`, POSIX-style redirection and append, shell identity spoofing, constrained VFS snapshots, user/root Capability profiles, VFS daemon rejection of missing processes, path-scoped hardware access, blocking `waitpid`, descriptor inheritance and offsets, negative `lseek`, default-deny VFS access, admin-gated Capability management, invalid signal rejection, and orphan auto-reaping. This is focused simulation coverage, not full POSIX conformance: complete signal delivery/handlers, process groups, exec image replacement, byte-oriented descriptor semantics, concurrent waiter races, actual browser Worker behavior, UI cancellation in a real browser, and resource exhaustion still need dedicated cases. Promote a feature from **Partial** only after checks cover its success, failure, authorization, cleanup, and cross-process behavior.
