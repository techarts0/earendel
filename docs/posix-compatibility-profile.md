# Earendel POSIX Compatibility Profile

This document describes behavior present in the repository, not the intended architecture. Earendel is a browser-hosted teaching simulation: its VFS, process table, syscalls, network, and devices do not provide host-kernel isolation or full POSIX conformance.

## Status vocabulary

- **Implemented (simulated):** behavior is wired through the in-browser kernel/service model.
- **Partial:** a useful subset exists, but observable behavior differs from POSIX or important cases are missing.
- **Not implemented:** no corresponding POSIX behavior is currently provided.

## Process and syscall surface

| Surface | Status | Current behavior and limits |
| --- | --- | --- |
| `read`, `write`, `open`, `close`, `stat`, `lseek` | Partial | Operate on Earendel VFS nodes and per-PCB descriptor maps. Capability and VFS permission checks apply to path access. Descriptor offsets, `SEEK_END`, read lengths, and write results use UTF-8 byte counts. Individual VFS writes are capped at 32 MiB; an FD write past the cap fails with `EFBIG` before allocating a sparse buffer and leaves its offset unchanged. Data is still exposed as JavaScript strings, so arbitrary binary buffers and incomplete UTF-8 sequences do not have full POSIX byte-buffer semantics. Descriptors are numeric but are not host file descriptors. `lseek` supports `SEEK_SET`, `SEEK_CUR`, and `SEEK_END` for regular VFS files. |
| `fork` | Partial | Allocates a child PCB and one simulated user page, copies capabilities, and duplicates the descriptor table while sharing open-description offsets. It does not clone the parent's memory, environment, signal mask, or execution context. |
| `execve` | Partial | Checks directory traversal and the caller's execute permission on a regular VFS file, then reads the path and returns its content/arguments to the caller. It does not replace the current process image. Shell dispatch separately interprets supported `.sh` and `.eaf` content. |
| `exit` and `waitpid` | Partial | Exit records an integer status and revokes the process endpoint/capabilities and simulated user page. A direct parent can block while the child runs; exit wakes one waiter and reaps the zombie. Orphans are adopted by simulated PID 1 and auto-reaped on exit. Invalid/non-child waits return `ECHILD`. This is a single-PID wait interface, not the full `waitpid(2)` option and status encoding contract. |
| `kill` and signals | Partial | `SIGKILL` and `SIGTERM` terminate the target with status `128 + signal`; `SIGSTOP`/`SIGCONT` change the simulated state; a small set of other signals is queued. There are no signal handlers, masks, delivery points, process groups, or full POSIX signal semantics. |
| Scheduling and memory | Partial | The scheduler tracks PCB states and a small simulated page table. `sched-policy` stores a policy label but does not schedule browser execution; CPU time, wait time, and kernel priority are therefore reported as unavailable. `sched-stat` reports actual PCB state-transition counts instead of generated context-switch estimates. The scheduler does not preempt JavaScript execution, clone address spaces, provide copy-on-write, or enforce a real MMU boundary. |
| errno and syscall ABI | Partial | Calls return `{ code, data, error }` from TypeScript; this is not a C ABI, register convention, `errno` location, or binary syscall interface. Some syscall error strings and trace labels remain simplified. |

The syscall numbers and current dispatch are defined in [`src/kernel/types.ts`](../src/kernel/types.ts) and [`src/kernel/syscall.ts`](../src/kernel/syscall.ts). Process behavior is implemented by [`src/kernel/taskScheduler.ts`](../src/kernel/taskScheduler.ts) and [`src/kernel/services/pmd.ts`](../src/kernel/services/pmd.ts); VFS descriptor behavior is in [`src/kernel/services/vfsd.ts`](../src/kernel/services/vfsd.ts). A runnable in-OS probe is installed at `/home/hello/tests/posix-process-conformance.bats`; run it with `bats /home/hello/tests/posix-process-conformance.bats` to exercise nested child output and exit-status/wait/reap behavior.

## Shell language

Earendel provides a POSIX-inspired shell implemented in TypeScript, not `/bin/sh` or Bash. The parser/interpreter supports a growing subset including command sequencing, pipelines, redirection, logical operators, variables, functions, conditionals, loops, and selected parameter expansions. Its BATS runner supports `@test`, `test_case`, basic assertions, and a `run` helper exposing `$status`, `$output`, and `$lines`; it is not full Bats-core compatibility. Pipelines pass strings between commands in sequence; they are not concurrent processes connected by kernel pipes. Job control, terminal process groups, complete quoting/expansion rules, and full shell grammar are not implemented.

Relevant implementation: [`src/core/shellParser.ts`](../src/core/shellParser.ts), [`src/core/shellEngine.ts`](../src/core/shellEngine.ts).

## WASM/WASI

The WASM runtime instantiates modules in the browser and supplies selected `wasi_snapshot_preview1` imports. Implemented imports include output, argument sizing, exit signaling, clock, and randomness. Several imports are stubs (for example `fd_close`, `fd_seek`, and environment retrieval); filesystem, process, socket, polling, and complete WASI error semantics are not available. Therefore “WASI-compatible” must be scoped to the imports actually implemented by [`src/core/wasmRuntime.ts`](../src/core/wasmRuntime.ts), not treated as general POSIX support.

## Capability and Agent boundary

Kernel authorization is deterministic and runs before the advisory Agent observation hook. Syscall observations are copied into a bounded queue (256 pending entries; oldest entries are dropped under pressure), and raw syscall string payloads are summarized before observers receive them. The queue advances without waiting for inference or actions. At most 32 Agents can be registered, and each Agent can process only one observation at a time; Agent work for a given event is started concurrently. This allows responsive Agents to process later events while a stalled Agent awaits its 35-second response deadline. An Agent that exceeds the deadline is disabled; stop, timeout, or Agent replacement invalidates its pending inference before `act`, while synchronous JavaScript still cannot be preempted on the main thread. Unknown processes do not get implicit syscall identity; VFS and network services also check capabilities at their service boundary. Interactive users get scoped VFS rights, read-only access to shipped Skills under `/skills`, scoped `/dev/ai` access for inference, and scoped `/dev/wayland` and `/dev/fb0` access for desktop surfaces; other device access, networking, and admin capabilities require explicit grants. Kernel Agent processes and the Harness Skill process receive only the `/dev/ai` device grant needed for inference; the Skill's requested network access remains separately caller-approved and URL-scoped. The LLM configuration (including its API key) is owned by root with mode `0600`; the driver and trusted status helper read it internally, and users configure it with `sudo vi /etc/llm.conf`. Authenticated root sessions receive the privileged profile, which is revoked when the shell returns to the prior user. Device writes go through vfsd and the originating process endpoint; direct VFS.writeFile() calls cannot trigger hardware effects. Hardware driver actions require path-scoped CAP_DEVICE_IO, network operations require CAP_NET_ADMIN, Wayland surface creation and framebuffer flush check their device scopes in waylandd, surfaces are owned by their creating PID and stale surfaces are pruned after process exit, and raw writes to /dev/skill are rejected in favor of the Skill command with explicit grants. `/dev/ai` access through scoped VFS and vfsd open/read/stat operations, inference syscalls, and direct driver IPC require CAP_DEVICE_IO for `/dev/ai`. cap-grant, cap-revoke, and whole-system snapshot save/restore require CAP_SYS_ADMIN; because kernel admin checks are process-wide, CAP_SYS_ADMIN accepts only the `*` scope and cannot be presented as a narrower grant. cap-list can inspect only the caller's own process unless the caller has that capability. Skill manifest permissions are requests: the caller must grant matching scopes/tools with skill --grant-read=PATH, skill --grant-write=PATH, skill --grant-tool=NAME, skill --grant-mcp=SERVER/TOOL, --grant-network, and/or --grant-memory. MCP tool authorization is exact to the `SERVER/TOOL` pair, and the client rechecks the active caller PID and URL-scoped CAP_NET_ADMIN before fetching; MCP listings show only authorized server names and omit full URLs. Effective permissions are restricted to the intersection of the manifest request and caller grants, then recorded in the session audit. UI launches without supplied grants receive no extra grants. IPC trace access and controls require CAP_SYS_ADMIN, and the ring buffer stores redacted payload types/string lengths without enumerating object contents. Harness actions/outputs, references, inherited memory, Skill instructions, and inference context have explicit size/count limits; manifest timeouts are capped at ten minutes.

In browser builds, EAF JavaScript runs in a dedicated Worker. At most 8 EAF Workers run concurrently, and each Worker may have at most 64 active OS RPC calls; overload fails with `EAGAIN`. The Worker removes direct network, storage, device, and nested Worker APIs; OS-facing methods use RPC bound to the forked child PID and its scoped VFS. Calls crossing that RPC boundary are asynchronous. Execution has a 60-second deadline, and RPC count, aggregate message size, logs, and returned values are bounded. Kernel services themselves still run on the browser main thread; there is no Worker-backed vfsd, pmd, or driverd. The app's Content Security Policy permits Blob Workers and same-origin module scripts while disallowing external module imports; deployments that replace this policy must preserve those restrictions. If Worker or Blob URL support is unavailable, browser execution fails closed. The Worker is a useful application sandbox, not a host-kernel security boundary: the browser controls CSP and resource quotas, same-origin module code remains within the trust boundary, and this simulation does not provide an MMU or protection against browser implementation flaws. Non-browser SSR/verifier execution still uses the in-process evaluator and must not be treated as an untrusted-code environment.

VFS snapshots are persisted in browser local storage and require a live process with `CAP_SYS_ADMIN`. Saving is atomic with respect to the in-memory index and reports failure if storage is unavailable or over quota. The implementation accepts at most 16 records, 2 MiB of serialized storage, and 1.5 MiB of UTF-8 node data per snapshot; larger images are rejected before encoding. Restore validates the complete node table and metadata before mutation, restores symbolic POSIX permission strings through numeric modes, and leaves volatile `/dev`, `/proc`, `/sys`, and `/run` trees live rather than replaying stale runtime nodes.

## Simulated subsystems

Networking and firewall decisions are educational simulations layered over browser APIs. HTTP(S) fetch uses browser `fetch` after simulated capability/firewall checks; redirects fail closed so a request cannot silently leave its approved URL scope. `netd` caps each process at 8 concurrent fetches, URL length at 2,048 characters, request headers at 64 (each value at most 8,192 characters), request bodies at 1 MiB, and streamed response bodies at 1 MiB. Response bodies are cancelled when the byte limit is exceeded, including when the server omits or misstates `Content-Length`. Browser policy still controls actual network access. DNS is simulated, WebSocket is browser-backed, WebRTC sockets are mocked, and `listen` returns a simulated listener identity. Raw sockets, arbitrary bind/listen/accept, packet access, and host firewall control are not provided.

## Verification policy

Skill session audit records are root-owned and bounded to 512 KiB per session file, 2,048 files, and 16 MiB total under `/var/log/harness`; quota exhaustion or persistence failure rejects the Skill run rather than reporting success.

Each Skill session retains at most 500 audit events. Once that bound is reached, the record preserves the first 499 events plus an `audit-truncated` marker and a `droppedEvents` count, so readers can distinguish a bounded partial trace from a complete one.

Agent action history records the boolean result from `act()`; an Agent action rejected by its executor is not represented as successfully acted.

Skill `curl`, `wget`, and `fetch` commands require an explicit HTTP(S) URL and are checked against the executing Skill PID's granted `CAP_NET_ADMIN` URL scopes before command dispatch. Network utilities without a reviewed Skill command profile remain denied; download output paths also require an approved VFS write scope.

Capability VFS directory snapshots are bounded to 10,000 nodes, 20,000 traversal steps, and 32 MiB of readable file content per operation. Exceeding a bound fails with `E2BIG`; ShellEngine reports the command error instead of returning a silently incomplete tree.

`kill(pid, 0)` checks target existence and caller authority without queuing or delivering a signal; unsupported signal numbers are rejected before process state changes.
